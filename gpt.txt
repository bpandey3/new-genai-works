Recommendation: Adopt KServe as enterprise-standard model serving abstraction on EKS.

Reason:
KServe aligns with Kubernetes-native governance, namespace isolation, CRD lifecycle control, and enterprise RBAC — which are stronger requirements than developer agility advantages provided by Ray Serve.

2️⃣ Architectural Philosophy Comparison
KServe
Kubernetes-native CRD

Declarative model lifecycle

Control plane driven

Infra-owned abstraction

Works inside existing EKS governance

Ray Serve
Python-native serving abstraction

Runs on Ray cluster

Application-driven lifecycle

Dev-owned abstraction

3️⃣ Control Plane Deep Dive
KServe Control Plane
Components:

KServe Controller (watches InferenceService CRD)

Knative Serving (revision + autoscaling)

Istio (traffic routing + mTLS)

Kubernetes API server

Flow:

User applies InferenceService YAML

CRD stored in etcd

KServe controller reconciles

Creates Knative Service

Knative creates Deployment + Revision

Istio routes traffic

Ray Serve Control Plane
Components:

Ray Head Node

Ray Global Control Store (GCS)

Ray Scheduler

Ray Workers

Flow:

Python code registers deployment

Ray control plane manages actors

Ray scheduler assigns resources

Kubernetes only manages Ray pods

This means:

Kubernetes does not understand model abstraction

Governance moves to Ray layer

That is a major architectural distinction.

import ray

1️⃣1️⃣ Anticipated Tough Questions
Q: Why not Ray if GPU efficiency is better?
Answer:

GPU efficiency is valuable, but isolation, auditability, and failure containment are higher priority in regulated enterprise workloads. We can optimize GPU pools within Kubernetes node groups without introducing shared runtime risks.

Q: What about LLM serving?
Answer:

For heavy LLM batching workloads, Ray may be evaluated as specialized runtime. But core enterprise inference platform should remain Kubernetes-native.

Q: Does Knative cold start impact latency?
Answer:

Yes, for scale-to-zero. Mitigation:

Min replicas = 1 for critical workloads

Warm GPU pools

Concurrency tuning

Q: What is exit strategy?
Answer:

Since KServe is Kubernetes-native CRD, models remain container-based. Migration to alternative serving solution would require minimal app changes.

Ray creates stronger runtime coupling.
